## 1. Обзор

Mirror — Discord-бот и веб-дашборд для государственных фракций сервера GTA5RP: документы, розыск, штрафы, нашивки, регистрации транспорта и униформы, переводы между фракциями, кадровый аудит, IC чёрный список, формы, обращения.

```text
        Discord                                Браузер
           │ команды, кнопки, формы              │ HTTPS
           ▼                                     ▼
   ┌───────────────┐                     ┌────────────────┐
   │   apps/bot    │                     │ apps/dashboard │  Next.js 15, Auth.js
   │  discord.js   │                     │  страницы+API  │
   └───────┬───────┘                     └────────┬───────┘
           │            packages/core             │
           └──────────►  правила, аудит,  ◄───────┘
                         настройки, очередь
                              │
                        packages/db (Prisma)
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
        PostgreSQL 16                 S3-хранилище (SeaweedFS)
```

Два процесса — бот и дашборд — не вызывают друг друга напрямую. Их связывают база данных и очередь задач в ней:

- **дашборд → бот:** дашборд меняет запись и кладёт задачу (`jobs`); бот забирает её и делает то, что может сделать только он — пишет в Discord, выдаёт роли;
- **бот → дашборд:** бот пишет в базу снимок серверов, записи модулей и сигнал «жив»; дашборд их читает.

Поэтому любой из двух процессов можно перезапустить отдельно, а задачи, поставленные во время простоя бота, выполнятся после его запуска.

## 2. Репозиторий

Монорепозиторий на pnpm workspaces. TypeScript strict (`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`), модули ESM (NodeNext), Node.js ≥ 22.9.

```text
apps/
  bot/src/
    index.ts          запуск, события Discord, таймеры, завершение
    commands.ts       описание slash-команд и их регистрация
    slash.ts          обработчики slash-команд и проверка прав
    buttons.ts        кнопки, выпадающие списки, модальные окна
    handlers.ts       обработчики задач очереди (всё, что уходит в Discord)
    worker.ts         воркер очереди
    cp-sync.ts        синхронизация доступов сервера ЧП
    admin-roles.ts    выдача глобальных admin-ролей
    guard.ts          аварийная блокировка, технические баны, отчёт об ошибках
    snapshot.ts, sync.ts   снимок серверов, ролей, участников
    stage4-review.ts  карточки заявок (регистрации, переводы)
    embed-payload.ts  перевод описания сообщения в формат discord.js
  dashboard/src/
    app/              страницы и API (App Router)
    components/       компоненты интерфейса
    lib/              доступ, сессии, утилиты сервера
    auth.ts           Auth.js: вход через Discord, сессии
    middleware.ts     первичная проверка «вошёл ли»
    instrumentation*.ts  сторож: оповещение, если бот замолчал
packages/
  core/src/           вся доменная логика (см. 2.1)
  db/prisma/          schema.prisma и миграции
deploy/               установка, обновление, домен, systemd, Caddy, резервные копии
scripts/              maintenance.mjs, provision-test-discord.ts
test/                 общие хелперы и глобальная настройка тестов
docs/                 PLAN, TECHNICAL, DEPLOYMENT, DEVLOG
```

Зависимости направлены в одну сторону: `apps/*` → `packages/core` → `packages/db`. Приложения используют собранный `packages/core/dist`, поэтому после правки ядра нужна его сборка.

## 3. Принципы, которые держит код

1. **Всё настраивается в дашборде.** Идентификаторов серверов, каналов, ролей и вебхуков в коде и в `.env` нет. Любая роль (кто может выполнить команду, кого упомянуть) выбирается из снимка ролей сервера.
2. **Ничего не удаляется физически.** У записей есть статус (`ACTIVE`, `CLOSED`, `EXPIRED`, `REVOKED`, `ARCHIVED`); «удаление» — смена статуса. Исключение — перенос журнала аудита в архивную таблицу (строка переезжает, а не исчезает).
3. **Каждое изменение — в журнал аудита**, в той же транзакции, что и само изменение.
4. **Бизнес-правила — в ядре.** Бот и дашборд только вызывают функции ядра, поэтому правило, добавленное один раз, действует в обоих.
5. **Ошибка для человека — `UserError`.** Её текст написан по-русски и показывается как есть; всё остальное пользователь видит как «внутренняя ошибка», а подробности идут в журнал.
6. **Discord — только через очередь.** Обработчик команды сохраняет запись и ставит задачу; сообщение отправляет воркер. Сбой Discord не теряет запись.

## 4. Окружение и секреты

В `.env` лежат только секреты и адрес сайта. Переменные проверяются схемами zod при старте процесса; ошибка перечисляет неверные.

| Переменная | Кто читает | Назначение |
|---|---|---|
| `APP_ENV` | оба | `development` / `test` / `production` |
| `LOG_LEVEL` | оба | уровень журнала pino, по умолчанию `info` |
| `DATABASE_URL` | оба | строка подключения PostgreSQL |
| `SUPER_ADMIN_USER_IDS` | оба | Discord ID главных администраторов через запятую |
| `PUBLIC_BASE_URL` | оба | адрес сайта для ссылок на веб-формы; по умолчанию `http://localhost:3000` |
| `DISCORD_BOT_TOKEN` | бот | токен бота |
| `DISCORD_CLIENT_ID` | оба | приложение Discord |
| `DISCORD_CLIENT_SECRET` | дашборд | вход через Discord |
| `OAUTH_REDIRECT_URL` | дашборд | `<адрес>/api/auth/callback/discord`; из него же берётся базовый адрес Auth.js |
| `SESSION_SECRET` | дашборд | подпись сессионной cookie, не короче 16 символов |
| `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET` | оба | хранилище файлов |
| `POSTGRES_PASSWORD`, `BACKUP_AT`, `BACKUP_KEEP_DAYS` | Docker Compose | пароль базы и расписание резервных копий (в разработке — значения по умолчанию) |
| `NEXT_DIST_DIR` | сборка | проверочная сборка в отдельную папку рядом с работающим dev-сервером |
| `INSTANCE_LABEL` | дашборд | надпись в верхней панели («Тестовая копия» у тестовой установки); необязательна |
| `POSTGRES_PORT`, `S3_PORT` | Docker Compose | порты базы и хранилища на `127.0.0.1` (по умолчанию 5432 и 9000; у тестовой копии 5433 и 9001) |
| `DEPLOY_BRANCH` | `update.sh` | ветка, за которой следует установка; по умолчанию `main` |

Приложения читают корневой `.env` через `node --env-file-if-exists=../../.env`; на сервере — `--env-file=/opt/mirror/.env` в unit-файлах systemd.

## 7. Кто есть кто и права

`resolveIdentity(discordUserId, { superAdminUserIds })` вычисляет права по снимку Discord и `role_mappings`:

- учитываются активные серверы, где пользователь сейчас состоит, и роли, которые у него там есть;
- **уровень администрации** берётся только с главного сервера, выбирается наивысший; ID из `SUPER_ADMIN_USER_IDS` — всегда главный администратор;
- **фракция**, лидер / заместитель, ранг и отделы — с сервера, привязанного к фракции;
- отдельные права (`PERMISSION`) собираются со всех серверов.

| Уровень | Функция | Что может |
|---|---|---|
| игрок (вошёл через Discord) | — | профиль, каталог ТС, калькулятор, FAQ, реестр IC ЧС, свои сессии |
| Хелпер и выше | `canViewModules` | читать реестры, статус системы, выгружать CSV |
| Админ и выше | `canManageModules` | действия над записями реестров, технические баны, статистика, каталог и FAQ, публичные ссылки |
| Главный администратор | `canManageSystemSettings` | все настройки, формы, сообщения, журнал аудита, очередь задач, чужие сессии, блокировка, admin-роли |

Права команд бота, не привязанные к уровню, задаются списками ролей в настройках (раздел 6): пока список пуст, действует правило по умолчанию; администраторы могут всегда. Никто не принимает решение по собственной заявке — проверка в `decideRegistration` и `decideTransfer`.

Проверка в дашборде двухступенчатая: `middleware.ts` отправляет гостя на вход, а каждая страница и каждый маршрут API заново вычисляют права по свежим данным (`lib/session.ts`: `requireSignedIn`, `requireIdentity`, `requireModuleManager`, `requireSystemSettings`). Данные в сессионной cookie решают только, какие пункты меню показать.

## 8. Аудит

`auditedMutation(context, action, entityType, run)` выполняет изменение и запись в журнал в одной транзакции: изменения без записи не бывает. Запись хранит инициатора (`USER` / `BOT` / `SYSTEM`, пользователь, Discord ID в метаданных), действие, сущность, источник (`bot.slash`, `discord.button`, `dashboard`, `deploy`…), сервер и канал, IP (для дашборда), снимки «было» и «стало».

Записи старше `audit.archiveAfterDays` бот переносит в `audit_log_archive` пакетами по 1000 при каждом обслуживании. Страница журнала — `/audit` (фильтры по действию, сущности, автору, периоду).

## 9. Очередь задач

Таблица `jobs`. Всё, что бот делает в Discord по поручению, — задача.

- **Постановка:** `enqueueJob({ type, payload, maxAttempts })`, часто внутри транзакции с изменением записи.
- **Захват:** один запрос `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED) RETURNING` — задача не выдаётся двум воркерам.
- **Повтор при ошибке:** задержка `5 с · 2^(попытка−1)`, не больше 10 минут; после `maxAttempts` (по умолчанию 5) — `FAILED`, сообщение в канал ошибок.
- **Откладывание:** обработчик возвращает `{ status: "deferred", reason }`, если цель не настроена (нет канала). Задача возвращается в очередь на 5 минут без расхода попыток; при сохранении настроек в дашборде такие задачи запускаются сразу (`wakeDeferredJobs`); через 7 дней ожидания — `FAILED`.
- **Зависшие:** `RUNNING` дольше 5 минут возвращаются в очередь.
- **Ровно одна отправка:** `runOnce(job, key, …)` записывает результат шага в `job.result.steps` сразу после отправки; повтор задачи находит запись и не публикует сообщение второй раз.
- **Воркер бота:** опрос раз в 2 секунды, до 20 задач за такт, до трёх задач одновременно. Задачи одной записи (общий `…Id` в данных задачи) выполняются строго по очереди. Задачу, поставленную самим ботом, воркер берёт сразу: `onJobEnqueued` будит его без ожидания опроса.
- **Управление:** страница `/jobs` — повторить упавшую или отменённую, отменить ожидающую.
- **Отложенная отправка:** `scheduleMessageDesignSend` ставит `message_design.send` с `available_at` на выбранное время (не дальше 90 дней) и `scheduledFor` в данных; воркер берёт её не раньше этого времени. Список — `listScheduledMessageSends`, отмена — `cancelScheduledMessageSend`; оба действия в журнале аудита. Проверка очереди в статусе служб считает только задачи, чьё время уже наступило.
- **Чтение сообщения для редактора:** `message_design.import` (одна попытка) — бот читает сообщение через REST и возвращает в результате задачи шаблон или причину отказа; редактор опрашивает `GET /api/settings/embeds?importJob=<id>`. Неверная ссылка — ответ человеку, а не сбой: в канал ошибок она не попадает.

Типы задач (`MODULE_JOB_TYPES`): `document.send`, `document.response.send`, `wanted.publish`, `wanted.edit_closed`, `fine.publish`, `fine.edit_paid`, `fine.overdue`, `fine.refresh`, `cp.reconcile`, `personnel.publish`, `personnel.kick`, `message_design.send`, `message_design.resend`, `message_design.import`, `registration.review`, `registration.decided`, `registration.expired`, `transfer.review`, `transfer.decided`, `role_panel.publish`, `role_panel.archive`, `feedback.ticket_notify`, `feedback.reply_send`, `feedback.closed_send`, `feedback.open_publish`, `form.submission_deliver`, `form.open_publish`, `token.receive_publish`, `webhook_request.notify`, `ic_blacklist.publish`, `ic_blacklist.edit_closed`, `admin_roles.apply`.

## 10. Бот

discord.js 14. Интенты: `Guilds`, `GuildMembers` (в Developer Portal включить **Server Members Intent**); `GuildPresences` — только при `presence.enabled`.

**Статус «в сети».** Набор интентов задаётся при входе, поэтому бот читает `presence.enabled` до подключения. Изменения статуса (не активности) копятся и пишутся в `user_presences` раз в 5 секунд; после подключения и при часовой синхронизации пишется полный снимок — кого бот не видит, тот «не в сети». Сигнал «жив» несёт `presence: true|false`; профиль показывает статус только при свежем сигнале с `presence: true`. Переключатель в дашборде меняется — бот при очередном сигнале «жив» завершается с кодом 1, systemd поднимает его с новым набором интентов. Discord отказал в интенте (`disallowed intents`) — бот выключает `presence.enabled` (запись в журнале аудита от `bot.presence_intent_rejected`) и завершается; следующий запуск идёт без него.

### 10.1 Жизненный цикл

При подключении: синхронизация всех серверов (сервер, роли, каналы, участники без ботов) → регистрация slash-команд → запуск воркера → таймеры.

| Таймер | Период | Что делает |
|---|---|---|
| сигнал «жив» | 30 с | строка `bot` в `service_heartbeats` |
| воркер очереди | 2 с | задачи |
| полная синхронизация и сверка ЧП | 1 ч | снимок серверов, `reconcileCpAccess` |
| обслуживание | 10 мин | истечение регистраций, документов и записей ЧС; автозакрытие нерассмотренных заявок; уведомления о просроченных штрафах; архив журнала |

События ролей и каналов собираются в один пересчёт на сервер (debounce 2 с). `SIGINT` / `SIGTERM` — корректная остановка. Необработанное исключение — журнал, сообщение в канал ошибок, завершение с кодом 1; процесс поднимает systemd (`Restart=on-failure`).

### 10.3 Кнопки и формы

`custom_id` кнопки — `mirror:<действие>:<id>`; id указывает на строку `button_actions` с параметрами. ### 10.4 Синхронизация ЧП

Роли на сервере ЧП выдаются по фракционным ролям на серверах фракций; у кого их нет — исключается. Защита от ошибок:

- «не удалось прочитать сервер» не значит «не состоит»: такой участник пропускается;
- полная сверка сначала считает все решения; если исключений больше предела (`cp.maxKickPercent`, но не меньше трёх человек), **никто не исключается**, в лог-канал уходит предупреждение, в аудит — событие `cp.kicks_held`;
- «сухой прогон» (`cp.dryRun`) только пишет, что было бы сделано;
- сверку можно запустить из дашборда (задача `cp.reconcile`), отчёт показывается на странице.

### 10.5 Что проверяется до любой команды

`guard.ts`: аварийная блокировка (действует не позже чем через 10 секунд после включения) и технический бан аккаунта. Главные администраторы блокировку проходят.

### 11.4 Стили

`globals.css` — общая тема; `player.css` подключается после него и содержит стили разделов этапов 5–7 и слой дизайн-системы: одна шкала шрифта (13 / 14 / 15 / 17 / 26 px, переменные `--fs-*`), одна высота кнопок и полей (`--control-h`, 40 px; в строках таблиц — 32 px), вкладки `.settings-tabs`, переключатели `.toggle-row`. Все токены объявлены в `:root` в `globals.css`: радиусы `--r-sm/md/lg`, поверхности `--bg-2` (панель) и `--bg-3` (всплывающие блоки, тень `--shadow-pop`), цвета состояний (`--ok`, `--warn`, `--danger`, `--danger-ink`, `--info` и их `-soft`), цвета Discord для превью (`--dc-*`), шрифт заголовков и меток `--font-hud` (Oswald). В `player.css` — шкала шрифта, высоты контролов и утилиты `u-*`. Общие элементы — в `components/ui.tsx` (`EmptyState`, `Plate`, `Money`, `Stamp`, `WantedStars`, `FactionBadge`, `MoreMenu`, скелетоны) и `components/copy-button.tsx` (`CopyButton`, `LinkActions`); `ui.tsx` не импортирует ядро, поэтому его используют и клиентские компоненты. Цвет фракции страницы берут через `getFactionColors()` из `lib/catalog.ts`. На телефоне таблицы `.registry-table` показываются карточками: оболочка (`app-shell.tsx`) копирует заголовки колонок в `data-label` ячеек. Вкладки страниц хранятся в адресе (`?tab=`) и рисуются компонентом `PageTabs`. Подтверждения — собственный диалог (`lib/confirm.ts`, `RegistryActions`), браузерный `confirm` не используется. Служебные страницы (нет доступа, 404, ошибка, техработы) собраны компонентом `NoticePage` из блоков страницы входа.

**Темы.** Все оттенки акцента (`--accent-hover`, `--accent-soft`, `--accent-pill`, свечения) вычисляются из `--accent` через `color-mix`, поверхности и рамки — из `--bg-*`. Пресеты — блоки `:root[data-theme="midnight|emerald|crimson|graphite"]` в `globals.css`; «Mirror» — сам `:root`. Свой цвет ставится на `<html>` как `--accent` и `--accent-contrast` (тёмный или белый текст по яркости). Выбор хранится в `users.theme`, `users.accent_color` и в cookie `mirror-appearance`: скрипт в `<head>` (`lib/appearance.ts`) применяет его до первой отрисовки, `AppearanceSync` в оболочке приводит cookie к значению из профиля на новом устройстве.

## 12. Хранилище файлов

S3-совместимое (локально и на сервере — SeaweedFS в Docker). `media.ts`: загрузка с проверкой типа и размера, чтение через `/api/media/[id]` с проверкой прав: хелперы и выше — любой файл, вошедший — фото каталога и файлы своих обращений (в том числе ответы администрации). PDF отдаётся на скачивание (`Content-Disposition: attachment`), картинки — для показа. Фото в публичной ссылке отдаётся только по живому токену ссылки, не по id файла. Файлы не удаляются.

## 13. Безопасность

- **Права на сервере** при каждом действии (раздел 7); интерфейс прав не определяет.
- **Сессии** отзываются мгновенно; бан завершает сессии.
- **Технический бан:** аккаунт — бот и сайт; статик — заявки. Главного администратора и самого себя забанить нельзя.
- **Аварийная блокировка** закрывает команды, кнопки, дашборд, публичные формы и ссылки для всех, кроме главных администраторов.
- **Публичные формы:** запрос только со своего адреса (проверка `Origin`), ограничение размера, скрытое поле-ловушка, срок действия и предел числа ответов. IP отправителя не хранится.
- **Вебхуки:** принимаются только адреса `https://discord.com/api/webhooks/…` — бот не отправит запрос на произвольный хост.
- **Публичные ссылки:** случайный токен 24 символа, краткая карточка без Discord ID и ссылок на форум, отзыв действует сразу.
- **CSV:** ячейки, начинающиеся с `= + - @`, экранируются.
- **Заголовки** (Caddy): HSTS, `nosniff`, запрет встраивания во фреймы.
- **Секреты** только в `.env` (права 600); база и хранилище слушают `127.0.0.1`.

## 14. Надёжность и наблюдение

- **Состояние служб** (`getSystemStatus`): база, бот (сигнал свежее 90 с), очередь (нет задач, ждущих дольше 5 минут), хранилище, резервные копии (не старше 26 часов). Смотрится командой `update.sh status` (`scripts/maintenance.mjs status`); отдельной страницы в дашборде нет — о неответившем боте и упавших задачах сообщает колокольчик.
- **Ошибки бота** — в канал `monitoring.errorChannelId`.
- **«Бот не отвечает»** — сторож в процессе дашборда (`instrumentation-node.ts`) раз в минуту проверяет сигнал и шлёт одно сообщение на вебхук за отключение; неудачная отправка повторяется.
- **Резервные копии** — контейнер `backup`: `backup.sh`, `verify.sh`, `restore.sh` (см. DEPLOYMENT.md).
- **Перезапуск при сбое** — systemd.

## 15. Разработка

```bash
cp .env.example .env            # вписать секреты Discord
docker compose up -d            # PostgreSQL :5432, S3 :9000, резервные копии
pnpm install
pnpm db:generate && pnpm db:deploy
pnpm build && pnpm db:seed
pnpm bot:start                  # бот
pnpm dashboard:dev              # http://localhost:3000
```

| Команда | Назначение |
|---|---|
| `pnpm check` | проверка типов всех пакетов и тестов |
| `pnpm lint` | ESLint |
| `pnpm test` | тесты на тестовой базе |
| `pnpm build` | сборка всего |
| `pnpm db:generate` / `db:deploy` / `db:status` / `db:seed` | Prisma |
| `NEXT_DIST_DIR=.next-check pnpm --filter @mirror/dashboard build` | production-сборка, не мешающая работающему dev-серверу |
| `node --env-file=.env scripts/maintenance.mjs status` | состояние служб из консоли |

Что стоит знать:

- после правки `packages/core` — `pnpm --filter @mirror/core build`, иначе бот и дашборд видят старое ядро; бот после этого пересобрать и перезапустить;
- на Windows `pnpm db:generate` может закончиться ошибкой `EPERM` при замене DLL движка, если запущен бот или дашборд; типы клиента при этом уже обновлены;
- код, которому нужен Node.js, нельзя импортировать из `instrumentation.ts` напрямую — только из ветки `NEXT_RUNTIME === "nodejs"`, иначе production-сборка падает на edge-варианте;
- репозиторий не отформатирован Prettier по умолчанию: не запускайте `pnpm format` на весь проект.

## 18. Известные ограничения

Перечень того, что не сделано или сделано не до конца, ведётся в PLAN.md, раздел 16. Главное с технической стороны:

- задачу, поставленную дашбордом, воркер увидит при следующем опросе (до 2 секунд): пробуждение работает только внутри процесса бота;
- ограничение частоты запросов хранится в памяти процесса дашборда и рассчитано на один экземпляр сайта;
- статус «в сети» работает только при включённом в Developer Portal Presence Intent;
- импорт `.xlsx` не переносит картинки внутри ячеек, диаграммы и сводные таблицы;
- страницы за входом не покрыты автоматическими тестами интерфейса.
