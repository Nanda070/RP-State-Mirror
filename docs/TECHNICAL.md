## 1. Обзор

Mirror — Discord-бот и веб-дашборд для государственных фракций сервера GTA5RP: документы, розыск, штрафы, нашивки, регистрации транспорта и униформы, переводы между фракциями, кадровый аудит, IC чёрный список, формы, обращения.

```text
        Discord                                Браузер
           │ команды, кнопки, формы              │ HTTPS
           ▼                                     ▼
   ┌───────────────┐                     ┌────────────────┐
   │   apps/bot    │                     │ apps/dashboard │  Next.js 15, Auth.js
   │  discord.js   │                     │  страницы+API  │
   └───────┬───────┘                     └────────┬───────┘
           │            packages/core             │
           └──────────►  правила, аудит,  ◄───────┘
                         настройки, очередь
                              │
                        packages/db (Prisma)
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
        PostgreSQL 16                 S3-хранилище (SeaweedFS)
```

Два процесса — бот и дашборд — не вызывают друг друга напрямую. Их связывают база данных и очередь задач в ней:

- **дашборд → бот:** дашборд меняет запись и кладёт задачу (`jobs`); бот забирает её и делает то, что может сделать только он — пишет в Discord, выдаёт роли;
- **бот → дашборд:** бот пишет в базу снимок серверов, записи модулей и сигнал «жив»; дашборд их читает.

Поэтому любой из двух процессов можно перезапустить отдельно, а задачи, поставленные во время простоя бота, выполнятся после его запуска.

## 3. Принципы, которые держит код

1. **Всё настраивается в дашборде.** Идентификаторов серверов, каналов, ролей и вебхуков в коде и в `.env` нет. Любая роль (кто может выполнить команду, кого упомянуть) выбирается из снимка ролей сервера.
2. **Ничего не удаляется физически.** У записей есть статус (`ACTIVE`, `CLOSED`, `EXPIRED`, `REVOKED`, `ARCHIVED`); «удаление» — смена статуса. Исключение — перенос журнала аудита в архивную таблицу (строка переезжает, а не исчезает).
3. **Каждое изменение — в журнал аудита**, в той же транзакции, что и само изменение.
4. **Бизнес-правила — в ядре.** Бот и дашборд только вызывают функции ядра, поэтому правило, добавленное один раз, действует в обоих.
5. **Ошибка для человека — `UserError`.** Её текст написан по-русски и показывается как есть; всё остальное пользователь видит как «внутренняя ошибка», а подробности идут в журнал.
6. **Discord — только через очередь.** Обработчик команды сохраняет запись и ставит задачу; сообщение отправляет воркер. Сбой Discord не теряет запись.

## 6. Настройки

Реестр — `packages/core/src/settings.ts`. У каждой настройки схема zod и значение по умолчанию; если строки в `system_settings` нет, возвращается значение по умолчанию. `setSetting` проверяет значение и пишет изменение в аудит. Главный сервер и сервер ЧП не могут совпадать.

| Группа | Ключи |
|---|---|
| Серверы | `core.mainGuildId`, `core.incidentGuildId` |
| Документы | `documents.ttlHours` (72), `documents.posterRoleIds`, `documents.responderRoleIds` |
| Розыск | `wanted.enabled`, `wanted.channelId`, `wanted.coordinatorRoleIds` |
| Штрафы | `fines.managerRoleIds` |
| Кадры | `personnel.managerRoleIds` |
| Нашивки | `tokens.expandThresholdPercent` (10), `tokens.finderRoleIds`, `tokens.openMessage` |
| Регистрации | `registrations.ttlDays` (31), `registrations.pendingTtlDays` (14), `registrations.vehicleChannelId`, `registrations.uniformChannelId`, `registrations.coordinatorRoleIds` |
| Переводы | `transfers.channelId`, `transfers.pingRoleIds`, `transfers.approvalDmText`, `transfers.pendingTtlDays` (14) |
| IC ЧС | `icBlacklist.enabled`, `icBlacklist.channelId`, `icBlacklist.managerRoleIds`, `icBlacklist.searchRoleIds` |
| Обратная связь, вебхуки, приглашения | `feedback.notifyChannelId`, `feedback.openMessage`, `webhooks.notifyChannelId`, `invites.guildIds`, `invites.defaultMaxAgeSeconds` |
| Синхронизация ЧП | `cp.syncEnabled`, `cp.excludedRoleIds`, `cp.logChannelId`, `cp.maxKickPercent` (10), `cp.dryRun` |
| Admin-роли | `adminRoles.byGuild` — для каждого сервера наборы ролей по четырём уровням |
| Надёжность | `system.lockdown`, `monitoring.errorChannelId`, `monitoring.alertWebhookUrl`, `monitoring.botDownAlertedAt` (служебная), `audit.archiveAfterDays` (365) |

**Кэш.** Бот включает кэш строк настроек на 5 секунд (`enableSettingsCache`): одна команда читает несколько настроек, и одни и те же читаются при каждом взаимодействии. Перед каждой задачей очереди кэш сбрасывается, чтение внутри транзакции кэш не использует, запись через `setSetting` сбрасывает ключ. Дашборд и тесты кэш не включают. Следствие: настройка, изменённая в дашборде, начинает действовать для команд бота не позже чем через 5 секунд.

Объявлены, но не используются: `app.timezone`, `backups.retentionDays`, `fines.dueDays`, `fines.channelId`, `fines.pingRoleIds`, `wanted.pingRoleIds`. В интерфейсе их нет; срок хранения копий задаёт переменная `BACKUP_KEEP_DAYS`, штрафы публикуются в канал документов фракции, пинг розыска строится из фракционных ролей.

## 7. Кто есть кто и права

`resolveIdentity(discordUserId, { superAdminUserIds })` вычисляет права по снимку Discord и `role_mappings`:

- учитываются активные серверы, где пользователь сейчас состоит, и роли, которые у него там есть;
- **уровень администрации** берётся только с главного сервера, выбирается наивысший; ID из `SUPER_ADMIN_USER_IDS` — всегда главный администратор;
- **фракция**, лидер / заместитель, ранг и отделы — с сервера, привязанного к фракции;
- отдельные права (`PERMISSION`) собираются со всех серверов.

| Уровень | Функция | Что может |
|---|---|---|
| игрок (вошёл через Discord) | — | профиль, каталог ТС, калькулятор, FAQ, реестр IC ЧС, свои сессии |
| Хелпер и выше | `canViewModules` | читать реестры, статус системы, выгружать CSV |
| Админ и выше | `canManageModules` | действия над записями реестров, технические баны, статистика, каталог и FAQ, публичные ссылки |
| Главный администратор | `canManageSystemSettings` | все настройки, формы, сообщения, журнал аудита, очередь задач, чужие сессии, блокировка, admin-роли |

Права команд бота, не привязанные к уровню, задаются списками ролей в настройках (раздел 6): пока список пуст, действует правило по умолчанию; администраторы могут всегда. Никто не принимает решение по собственной заявке — проверка в `decideRegistration` и `decideTransfer`.

Проверка в дашборде двухступенчатая: `middleware.ts` отправляет гостя на вход, а каждая страница и каждый маршрут API заново вычисляют права по свежим данным (`lib/session.ts`: `requireSignedIn`, `requireIdentity`, `requireModuleManager`, `requireSystemSettings`). Данные в сессионной cookie решают только, какие пункты меню показать.

## 8. Аудит

`auditedMutation(context, action, entityType, run)` выполняет изменение и запись в журнал в одной транзакции: изменения без записи не бывает. Запись хранит инициатора (`USER` / `BOT` / `SYSTEM`, пользователь, Discord ID в метаданных), действие, сущность, источник (`bot.slash`, `discord.button`, `dashboard`, `deploy`…), сервер и канал, IP (для дашборда), снимки «было» и «стало».

Записи старше `audit.archiveAfterDays` бот переносит в `audit_log_archive` пакетами по 1000 при каждом обслуживании. Страница журнала — `/audit` (фильтры по действию, сущности, автору, периоду).

## 9. Очередь задач

Таблица `jobs`. Всё, что бот делает в Discord по поручению, — задача.

- **Постановка:** `enqueueJob({ type, payload, maxAttempts })`, часто внутри транзакции с изменением записи.
- **Захват:** один запрос `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED) RETURNING` — задача не выдаётся двум воркерам.
- **Повтор при ошибке:** задержка `5 с · 2^(попытка−1)`, не больше 10 минут; после `maxAttempts` (по умолчанию 5) — `FAILED`, сообщение в канал ошибок.
- **Откладывание:** обработчик возвращает `{ status: "deferred", reason }`, если цель не настроена (нет канала). Задача возвращается в очередь на 5 минут без расхода попыток; при сохранении настроек в дашборде такие задачи запускаются сразу (`wakeDeferredJobs`); через 7 дней ожидания — `FAILED`.
- **Зависшие:** `RUNNING` дольше 5 минут возвращаются в очередь.
- **Ровно одна отправка:** `runOnce(job, key, …)` записывает результат шага в `job.result.steps` сразу после отправки; повтор задачи находит запись и не публикует сообщение второй раз.
- **Воркер бота:** опрос раз в 2 секунды, до 20 задач за такт.
- **Управление:** страница `/jobs` — повторить упавшую или отменённую, отменить ожидающую.

Типы задач (`MODULE_JOB_TYPES`): `document.send`, `document.response.send`, `wanted.publish`, `wanted.edit_closed`, `fine.publish`, `fine.edit_paid`, `fine.overdue`, `cp.reconcile`, `personnel.publish`, `message_design.send`, `message_design.resend`, `registration.review`, `registration.decided`, `registration.expired`, `transfer.review`, `transfer.decided`, `role_panel.publish`, `role_panel.archive`, `feedback.ticket_notify`, `feedback.reply_send`, `feedback.closed_send`, `feedback.open_publish`, `form.submission_deliver`, `form.open_publish`, `token.receive_publish`, `webhook_request.notify`, `ic_blacklist.publish`, `ic_blacklist.edit_closed`, `admin_roles.apply`.

## 10. Бот

discord.js 14. Интенты: `Guilds`, `GuildMembers` (в Developer Portal включить **Server Members Intent**).

### 10.1 Жизненный цикл

При подключении: синхронизация всех серверов (сервер, роли, каналы, участники без ботов) → регистрация slash-команд → запуск воркера → таймеры.

| Таймер | Период | Что делает |
|---|---|---|
| сигнал «жив» | 30 с | строка `bot` в `service_heartbeats` |
| воркер очереди | 2 с | задачи |
| полная синхронизация и сверка ЧП | 1 ч | снимок серверов, `reconcileCpAccess` |
| обслуживание | 10 мин | истечение регистраций, документов и записей ЧС; автозакрытие нерассмотренных заявок; уведомления о просроченных штрафах; архив журнала |

События ролей и каналов собираются в один пересчёт на сервер (debounce 2 с). `SIGINT` / `SIGTERM` — корректная остановка. Необработанное исключение — журнал, сообщение в канал ошибок, завершение с кодом 1; процесс поднимает systemd (`Restart=on-failure`).

### 10.2 Команды

|---|---|

### 10.3 Кнопки и формы

`custom_id` кнопки — `mirror:<действие>:<id>`; id указывает на строку `button_actions` с параметрами. Действия: `role.toggle`, `role.select`, `form.open`, `form.step`, `form.submit`, `registration.approve|reject`, `transfer.approve|reject` (по сторонам), `feedback.open`, `token.receive`, `personnel.kick`, `callback`. От повторных нажатий защищает кулдаун на пару «пользователь + кнопка».

Форма с пятью и менее полями — одно модальное окно; больше пяти — несколько шагов с черновиком в `form_drafts`. Поля, которых нет в Discord (выбор из списка, дата, флажок), делают форму веб-формой: кнопка ведёт на `PUBLIC_BASE_URL/f/<адрес>`.

### 10.4 Синхронизация ЧП

Роли на сервере ЧП выдаются по фракционным ролям на серверах фракций; у кого их нет — исключается. Защита от ошибок:

- «не удалось прочитать сервер» не значит «не состоит»: такой участник пропускается;
- полная сверка сначала считает все решения; если исключений больше предела (`cp.maxKickPercent`, но не меньше трёх человек), **никто не исключается**, в лог-канал уходит предупреждение, в аудит — событие `cp.kicks_held`;
- «сухой прогон» (`cp.dryRun`) только пишет, что было бы сделано;
- сверку можно запустить из дашборда (задача `cp.reconcile`), отчёт показывается на странице.

### 10.5 Что проверяется до любой команды

`guard.ts`: аварийная блокировка (действует не позже чем через 10 секунд после включения) и технический бан аккаунта. Главные администраторы блокировку проходят.

## 11. Дашборд

### 11.1 Вход и сессии

## 13. Безопасность

- **Права на сервере** при каждом действии (раздел 7); интерфейс прав не определяет.
- **Сессии** отзываются мгновенно; бан завершает сессии.
- **Технический бан:** аккаунт — бот и сайт; статик — заявки. Главного администратора и самого себя забанить нельзя.
- **Аварийная блокировка** закрывает команды, кнопки, дашборд, публичные формы и ссылки для всех, кроме главных администраторов.
- **Публичные формы:** запрос только со своего адреса (проверка `Origin`), ограничение размера, скрытое поле-ловушка, срок действия и предел числа ответов. IP отправителя не хранится.
- **Вебхуки:** принимаются только адреса `https://discord.com/api/webhooks/…` — бот не отправит запрос на произвольный хост.
- **Публичные ссылки:** случайный токен 24 символа, краткая карточка без Discord ID и ссылок на форум, отзыв действует сразу.
- **CSV:** ячейки, начинающиеся с `= + - @`, экранируются.
- **Заголовки** (Caddy): HSTS, `nosniff`, запрет встраивания во фреймы.
- **Секреты** только в `.env` (права 600); база и хранилище слушают `127.0.0.1`.

## 14. Надёжность и наблюдение

- **Статус** (`/status`, `getSystemStatus`): база, бот (сигнал свежее 90 с), очередь (нет задач, ждущих дольше 5 минут), хранилище, резервные копии (не старше 26 часов).
- **Ошибки бота** — в канал `monitoring.errorChannelId`.
- **«Бот не отвечает»** — сторож в процессе дашборда (`instrumentation-node.ts`) раз в минуту проверяет сигнал и шлёт одно сообщение на вебхук за отключение; неудачная отправка повторяется.
- **Резервные копии** — контейнер `backup`: `backup.sh`, `verify.sh`, `restore.sh` (см. DEPLOYMENT.md).
- **Перезапуск при сбое** — systemd.

```bash

pnpm install
```

| Команда | Назначение |
|---|---|
| `pnpm check` | проверка типов всех пакетов и тестов |
| `pnpm lint` | ESLint |
| `pnpm test` | тесты на тестовой базе |
| `pnpm build` | сборка всего |
| `pnpm db:generate` / `db:deploy` / `db:status` / `db:seed` | Prisma |
| `NEXT_DIST_DIR=.next-check pnpm --filter @mirror/dashboard build` | production-сборка, не мешающая работающему dev-серверу |
| `node --env-file=.env scripts/maintenance.mjs status` | состояние служб из консоли |

Что стоит знать:

- после правки `packages/core` — `pnpm --filter @mirror/core build`, иначе бот и дашборд видят старое ядро; бот после этого пересобрать и перезапустить;
- на Windows `pnpm db:generate` может закончиться ошибкой `EPERM` при замене DLL движка, если запущен бот или дашборд; типы клиента при этом уже обновлены;
- код, которому нужен Node.js, нельзя импортировать из `instrumentation.ts` напрямую — только из ветки `NEXT_RUNTIME === "nodejs"`, иначе production-сборка падает на edge-варианте;
- репозиторий не отформатирован Prettier по умолчанию: не запускайте `pnpm format` на весь проект.

## 18. Известные ограничения

Перечень того, что не сделано или сделано не до конца, ведётся в PLAN.md, раздел 16. Главное с технической стороны:

- кэшируются только настройки; фракции и привязки ролей бот читает из базы при каждом обращении;
- воркер опрашивает очередь раз в 2 секунды, а не будится при постановке задачи;
- обезличивание данных по запросу пользователя выполняется вручную, инструмента в дашборде нет;
- юридические тексты редактируются в коде, а не в дашборде;
- страницы за входом не проверены автоматическими тестами интерфейса.
