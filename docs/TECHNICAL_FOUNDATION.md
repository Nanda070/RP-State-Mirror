# Mirror: технический фундамент этапа 1

Документ описывает результат первого этапа плана проекта Mirror и является рабочей технической спецификацией для следующих этапов.

## 1. Зафиксированные решения

### 1.1 Целевой стек

Проект реализуется на TypeScript согласно `docs/PLAN.md`:

- монорепозиторий на pnpm workspaces;
- PostgreSQL 16 как основная база данных;
- Prisma как схема, миграции и типизированный клиент;
- MinIO как локальное S3-совместимое хранилище файлов;
- Discord-бот и веб-дашборд как отдельные приложения;
- общие правила, аудит и работа с задачами в `packages/core`;
- конфигурация проекта в базе данных, а не в исходном коде.

Java в текущей версии плана не является утвержденным стеком. Если решение будет изменено, это должно быть отдельным изменением `PLAN.md` с пересмотром архитектуры и этапа 1.

### 1.2 Старый Python-код

Файлы Python временно сохраняются как справочный источник поведения, форматов embed-сообщений и команд. Они не являются частью нового runtime.

Удаление допускается только после выполнения всех условий:

1. все используемые команды и фоновые задачи перенесены;
2. форматы данных и сообщений сопоставлены с новой схемой;
3. миграционный аудит подтвердил отсутствие нужных импортов и запуска Python;
4. тестовое окружение прошло smoke-тесты;
5. в dev blog записана дата и причина удаления.

До этого момента нельзя удалять Python-файлы или SQLite-логику как «неиспользуемые».

## 2. Структура монорепозитория

```text
mirror/
  apps/
    bot/                 Discord-бот, будущие slash-команды и worker jobs
    dashboard/           Next.js dashboard и API
  packages/
    core/                доменные сервисы, аудит, конфиг, очередь задач
    db/                  Prisma-схема и клиент PostgreSQL
  docs/
    PLAN.md              продуктовый план
    TECHNICAL_FOUNDATION.md
    DEVLOG.md
  docker-compose.yml     локальные PostgreSQL и MinIO
  docker-compose.test.yml изолированные тестовые сервисы
  package.json           команды workspace
  pnpm-workspace.yaml    workspace-пакеты
```

Границы зависимостей:

- `apps/*` могут зависеть от `packages/core`;
- `packages/core` может зависеть от `packages/db`;
- `packages/db` не зависит от приложений;
- бизнес-правила не должны дублироваться в боте и дашборде;
- ID Discord, каналов, ролей и webhook не размещаются в коде.

## 3. Конфигурация и секреты

`.env` содержит только секреты и bootstrap-доступ:

```text
DISCORD_BOT_TOKEN
DISCORD_CLIENT_ID
DISCORD_CLIENT_SECRET
OAUTH_REDIRECT_URL
DATABASE_URL
SESSION_SECRET
S3_ENDPOINT
S3_ACCESS_KEY
S3_SECRET_KEY
S3_BUCKET
SUPER_ADMIN_USER_IDS
```

Все остальные параметры являются данными конфигурации и после инициализации должны храниться в PostgreSQL. `SUPER_ADMIN_USER_IDS` нужен для входа и первичной настройки, когда главный Discord-сервер ещё не настроен.

## 4. Схема базы данных этапа 1

### `users`

Минимальный владелец Discord-аккаунта. На следующих этапах сюда будут добавлены профиль, персонажи и пользовательские настройки.

### `guilds`

Подключённые Discord-серверы. Поля `is_main` и `is_incident` разделяют главный сервер и сервер ЧП. Физическое удаление не используется: запись переводится в статус.

### `factions`

Справочник фракций, связанный с Discord-сервером. Роли, каналы и webhook будут добавлены отдельными сущностями при реализации конфигурационной части.

### `system_settings`

Ключ-значение для сроков, порогов, шаблонов и прочих изменяемых настроек. Значения валидируются схемами Zod на границе общего слоя.

### `audit_log`

Неизменяемая запись действия:

- тип и пользователь-инициатор;
- действие, тип и ID сущности;
- источник (`bot`, `dashboard`, `system` и т. п.);
- IP, guild и channel при наличии;
- снимки `before` и `after`;
- дополнительные структурированные метаданные.

Схема намеренно не содержит операции удаления. Архивация старых записей будет реализована позднее через `audit_log_archive`.

### `jobs`

Очередь команд «дашборд -> бот» на PostgreSQL:

- `PENDING` — ожидает обработки;
- `RUNNING` — захвачен worker’ом;
- `SUCCEEDED` — выполнен;
- `FAILED` — завершён ошибкой;
- `CANCELLED` — отменён явно.

Захват выполняется транзакционно. Полноценная retry/backoff-политика и watchdog для зависших задач относятся к следующим этапам.

## 5. Локальная инфраструктура

Запуск базовых сервисов:

```powershell
docker compose up -d
```

Сервисы:

| Сервис | Адрес | Назначение |
|---|---|---|
| PostgreSQL | `localhost:5432` | основная локальная БД |
| MinIO API | `localhost:9000` | S3 API |
| MinIO Console | `localhost:9001` | локальное управление хранилищем |

Тестовый контур не использует production-like volumes и слушает отдельные порты:

```powershell
docker compose -f docker-compose.test.yml up -d
```

| Сервис | Адрес |
|---|---|
| PostgreSQL test | `localhost:55432` |
| MinIO test API | `localhost:59000` |
| MinIO test Console | `localhost:59001` |

## 6. Команды разработки

```powershell
pnpm install
pnpm db:validate
pnpm db:generate
pnpm check
pnpm build
```

`db:validate` проверяет Prisma-схему без подключения к рабочей БД. `db:generate` генерирует клиент. `check` выполняет TypeScript-проверки пакетов, а `build` проверяет сборку workspace.

## 7. Что сознательно не входит в этап 1

- перенос конкретных slash-команд;
- OAuth и пользовательские сессии;
- UI дашборда;
- полноценный Discord worker;
- миграция исторической SQLite-базы;
- физическое удаление старого Python-кода;
- подключение Redis.

Эти задачи не должны появляться как скрытая часть фундаментального этапа.

## 8. Критерии готовности этапа 1

- workspace устанавливается через pnpm;
- Prisma-схема валидируется и клиент генерируется;
- PostgreSQL и MinIO поднимаются отдельно для локального и тестового контуров;
- общий слой содержит минимальные функции для настроек, аудита и jobs;
- README описывает новый способ запуска;
- архитектурные решения и процесс записаны в документации;
- старый Python-код помечен как временный reference layer и не удалён преждевременно.
