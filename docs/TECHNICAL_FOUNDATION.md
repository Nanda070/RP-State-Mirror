# Mirror: технический фундамент этапа 1

Документ описывает результат первого этапа плана Mirror и служит рабочей технической спецификацией для следующих этапов. Статус: **этап 1 закрыт** (2026-10-03).

## 1. Зафиксированные решения

### 1.1 Стек

- TypeScript (strict, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, ESM NodeNext);
- монорепозиторий на pnpm workspaces, Node.js 22.9+;
- PostgreSQL 16 и Prisma 6 (схема, миграции, типизированный клиент);
- S3-совместимое хранилище: локально и в тестах SeaweedFS (`weed mini`), в продакшене любой S3-совместимый сервис;
- Discord-бот (discord.js 14) и веб-дашборд (Next.js) как отдельные приложения;
- общие правила, аудит, настройки и очередь задач в `packages/core`;
- конфигурация проекта хранится в базе данных, не в коде.

### 1.2 Старый Python-код

Python-файлы временно хранятся как справочник по поведению, форматам embed-сообщений и командам. В новом runtime они не участвуют.

Удалять их можно только при выполнении всех условий:

1. все используемые команды и фоновые задачи перенесены;
2. форматы данных и сообщений сопоставлены с новой схемой;
3. проверка подтвердила, что Python нигде не импортируется и не запускается;
4. тестовое окружение прошло smoke-тесты;
5. в dev blog записаны дата и причина удаления.

## 2. Структура монорепозитория

```text
apps/
  bot/                 Discord-бот: снимок серверов, воркер очереди
  dashboard/           Next.js-дашборд и API (см. docs/STAGE_2.md)
packages/
  core/                аудит, настройки, очередь, снимок Discord, «кто есть кто», seed
  db/                  Prisma-схема, миграции, клиент
test/                  общие хелперы тестов и global setup
docs/                  PLAN, TECHNICAL_FOUNDATION, DEVLOG
.github/workflows/     CI
docker-compose.yml     локальные PostgreSQL и SeaweedFS
docker-compose.test.yml изолированный тестовый контур
```

Границы зависимостей:

- `apps/*` зависят от `packages/core` и `packages/db`;
- `packages/core` зависит от `packages/db`;
- бизнес-правила не дублируются в боте и дашборде;
- ID серверов, каналов, ролей и webhook не пишутся в код.

## 3. Конфигурация и секреты

В `.env` лежат только секреты и bootstrap-доступ. Prisma-команды читают корневой `.env` через `dotenv-cli`, приложения через `node --env-file-if-exists`. Если файла нет (CI), используются переменные окружения процесса.

| Переменная | Назначение |
|---|---|
| `APP_ENV`, `LOG_LEVEL` | окружение и уровень логов |
| `DATABASE_URL` | PostgreSQL |
| `DISCORD_BOT_TOKEN` | токен бота (обязателен для `apps/bot`) |
| `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `OAUTH_REDIRECT_URL` | вход в дашборд (Auth.js callback) |
| `SESSION_SECRET` | подпись JWT-сессий дашборда |
| `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET` | хранилище файлов |
| `SUPER_ADMIN_USER_IDS` | Discord ID главных админов через запятую (по умолчанию `1219803151180370021`) |

Переменные проверяются схемами zod (`packages/core/src/env.ts`) при старте. Ошибка перечисляет неверные переменные.

`SUPER_ADMIN_USER_IDS` нужен для первого входа и настройки, пока главный сервер ещё не выбран. Всё остальное (серверы, роли, каналы, сроки, пороги) хранится в БД и меняется из дашборда.

## 4. Схема базы данных

Физическое удаление не используется: у записей есть статус (`ACTIVE`, `ARCHIVED`, `DISABLED`), а у участников серверов отметка `is_present` и `left_at`.

| Таблица | Назначение |
|---|---|
| `users` | владелец Discord-аккаунта; профиль и персонажи добавятся позже |
| `guilds` | подключённые Discord-серверы; роль сервера (главный или ЧП) задаётся настройками, а не флагами |
| `discord_roles` | снимок ролей каждого сервера |
| `discord_guild_members` | снимок участников: ники, аватары, список ролей, присутствие |
| `role_mappings` | смысл роли: уровень доступа, участник, лидер или заместитель фракции, отдел, ранг, право |
| `factions` | справочник фракций и привязка к серверу фракции |
| `system_settings` | типизированные настройки |
| `audit_log` | неизменяемый журнал действий |
| `audit_log_archive` | архив старых записей журнала (ротация позже) |
| `jobs` | очередь команд «дашборд → бот» |

### 4.1 Настройки

Реестр в `packages/core/src/settings.ts`. Каждая настройка имеет схему zod и значение по умолчанию. Если записи в БД нет, возвращается значение по умолчанию.

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `core.mainGuildId` | `null` | главный сервер, единственный источник админских уровней |
| `core.incidentGuildId` | `null` | сервер ЧП: синхронизация ролей, розыск, регистрации |
| `app.timezone` | `Europe/Moscow` | часовой пояс отображения |
| `documents.ttlHours` | `72` | срок жизни документов |
| `registrations.ttlDays` | `31` | через сколько дней регистрация ТС или формы неактуальна |
| `tokens.expandThresholdPercent` | `10` | при каком остатке свободных номеров токены удлиняются на цифру |
| `transfers.approvalDmText` | текст про холл/собеседование | ЛС игроку после одобрения перевода обеими фракциями |
| `backups.retentionDays` | `14` | срок хранения бэкапов |

Главный сервер и сервер ЧП не могут совпадать: это проверяется при записи.

### 4.2 «Кто есть кто»

`resolveIdentity(discordUserId)` вычисляет права пользователя по снимку Discord и `role_mappings`:

- учитываются только активные серверы, на которых пользователь сейчас присутствует, и роли, которые у него действительно есть на этом сервере;
- админский уровень (`SUPER_ADMIN` > `SENIOR_ADMIN` > `ADMIN` > `HELPER`) берётся только с главного сервера, выбирается наивысший; ID из `SUPER_ADMIN_USER_IDS` всегда `SUPER_ADMIN`;
- фракция, лидер, заместитель, ранг (максимальный) и отделы берутся с сервера, привязанного к фракции;
- права (`PERMISSION`) собираются со всех серверов.

### 4.3 Начальные данные

`pnpm db:seed` создаёт отсутствующие фракции (GOV, FIB, LSPD, LSSD, SASPA, ARMY, EMS, WN), настройки по умолчанию и пользователей из `SUPER_ADMIN_USER_IDS`. Существующие записи не перезаписываются, каждое создание попадает в журнал от имени `SYSTEM`.

## 5. Аудит

- Каждое изменение данных идёт через `auditedMutation`: изменение и запись в журнал выполняются в одной транзакции.
- Запись хранит:
  - тип и ID инициатора;
  - действие, тип и ID сущности;
  - источник;
  - IP, сервер и канал;
  - снимки `before` и `after`;
  - метаданные.
- Контекст аудита валидируется до обращения к БД.
- События снимка Discord:
  - `guild.connected`, `guild.reconnected`, `guild.disconnected`;
  - `discord_role.created`, `discord_role.deleted`;
  - `member.joined`, `member.roles_changed`, `member.left`.
- Первая синхронизация сервера не пишется в журнал.

## 6. Очередь задач

Таблица `jobs`, статусы `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELLED`.

- **Захват:** `SELECT … FOR UPDATE SKIP LOCKED`, самая старая подходящая задача с `available_at <= now()`. Захват увеличивает `attempts` и проставляет `locked_by` и `locked_at`.
- **Завершение и ошибка:** выполняются только воркером, который держит задачу.
- **Повторы:** задержка `5 с · 2^(попытка−1)`, максимум 10 минут. После `max_attempts` (по умолчанию 5) статус `FAILED`. Повторы можно отключить для конкретной ошибки.
- **Зависшие задачи:** `RUNNING` дольше 5 минут возвращаются в `PENDING` или, если попытки кончились, в `FAILED`. Проверка раз в минуту.
- **Отмена:** только для `PENDING`.
- **Воркер бота:** опрашивает очередь раз в 2 секунды, за такт обрабатывает до 20 задач. Обработчики регистрируются в `apps/bot/src/handlers.ts`. Неизвестный тип задачи сразу получает `FAILED`.

## 7. Бот

- Интенты: `Guilds`, `GuildMembers`. В Developer Portal нужно включить **Server Members Intent**.
- При старте синхронизирует все серверы: сервер, роли, участников без ботов. Затем запускает воркер и повторяет полную синхронизацию раз в час.
- В реальном времени реагирует на события серверов, ролей и участников.
- Корректно завершается по SIGINT и SIGTERM: останавливает воркер, отключается от Discord и БД.

## 8. Локальная инфраструктура

Все порты слушают только `127.0.0.1`.

```powershell
docker compose up -d                              # PostgreSQL :5432, S3 :9000 (бакет mirror)
docker compose -f docker-compose.test.yml up -d   # PostgreSQL :55432, S3 :59000 (tmpfs)
```

## 9. Команды

| Команда | Что делает |
|---|---|
| `pnpm db:generate` / `db:validate` | генерация клиента, проверка схемы |
| `pnpm db:migrate` | новая миграция в разработке |
| `pnpm db:deploy` / `db:status` | применить миграции, статус |
| `pnpm db:seed` | начальные данные (нужен `pnpm build`) |
| `pnpm lint` | ESLint |
| `pnpm build` | сборка всех пакетов |
| `pnpm check` | проверка типов пакетов и тестов |
| `pnpm test` | интеграционные тесты на тестовой БД (`TEST_DATABASE_URL`, по умолчанию `localhost:55432`); миграции применяются автоматически |
| `pnpm bot:start` | запуск бота |
| `pnpm dashboard:dev` / `dashboard:start` | дашборд на `:3000` |

CI (`.github/workflows/ci.yml`) на каждый push в `main` и каждый PR выполняет install, generate, validate, lint, build, check и test на сервисе PostgreSQL.
