# Mirror: dev blog

## 2026-10-03 — старт этапа 1

### Исходное состояние

Репозиторий содержал Python-бота на `discord.py`, SQLite-слой и настройки Discord в `.env`. Такой код полезен для извлечения текущего поведения, но не соответствует целевой архитектуре из `PLAN.md`: в ней нужен монорепозиторий, PostgreSQL, MinIO, общий доменный слой, аудит и очередь задач.

### Принятое решение

Продолжить реализацию на TypeScript, потому что это явно указано в текущем плане проекта. Предположение о Java не меняет стек автоматически: оно требует отдельного утверждения и пересмотра `PLAN.md`.

### Сделано

- создан pnpm workspace;
- добавлены `apps/bot` и `apps/dashboard` как минимальные точки входа;
- добавлены `packages/core` и `packages/db`;
- добавлена Prisma-схема PostgreSQL для пользователей, серверов, фракций, системных настроек, аудита и jobs;
- добавлены функции общего слоя для чтения/записи системных настроек;
- добавлена валидация и запись событий аудита;
- добавлены enqueue и транзакционный claim для очереди jobs;
- добавлен основной Docker Compose с PostgreSQL и MinIO;
- добавлен отдельный тестовый Compose с временными томами и отдельными портами;
- создан этот технический документ и dev blog;
- Python-файлы оставлены без изменений как reference layer.

### Проверка

Локально обнаружены Node.js, pnpm и Docker. pnpm 11 потребовал явно разрешить install-скрипты Prisma; разрешены только `@prisma/client`, `@prisma/engines` и `prisma`. После этого успешно прошли `pnpm db:validate`, `pnpm db:generate`, `pnpm check` и `pnpm build`.

Docker CLI установлен, но Docker Desktop engine в момент проверки не был запущен, поэтому контейнерный smoke-test и применение миграции к PostgreSQL отложены до запуска Docker Desktop. Compose-конфигурации должны быть проверены командой `docker compose config` без обращения к daemon.

### Следующий шаг

Довести воспроизводимую установку зависимостей, проверить Prisma-схему и TypeScript-пакеты, затем добавить минимальные миграционные/health smoke-проверки. Перенос модулей бота начинается только после закрытия этих проверок.

### Правило удаления legacy-кода

Python удаляется в самом конце проекта, а не на этапе 1. Перед удалением нужно подтвердить покрытие всех команд и фоновых задач новой реализацией, отсутствие runtime-зависимостей и успешность тестового окружения.
