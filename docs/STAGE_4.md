# Mirror: этап 4 — новые модули бота

Статус: **в работе**. Этап не закрывается автоматически; изменение статуса требует отдельного разрешения пользователя.

## Цель

Добавить пользовательские и служебные модули поверх этапов 1–3: персонажи и статики, нашивки, регистрации ТС и униформы, переводы между фракциями, запрос webhook, IC чёрный список, служебные утилиты, панели ролей, обратная связь, формы внутри Discord.

## Схема данных

Миграция `20261003060000_stage4_modules` (идёт после миграций этапа 3):

- `characters` — до 3 активных персонажей; статик и слот уникальны только среди `ACTIVE` (частичные уникальные индексы), архивные записи не блокируют новые;
- `tokens` — глобально уникальный строковый номер, soft-revoke, одна `ACTIVE` нашивка на персонажа (частичный индекс), история отозванных сохраняется;
- `registrations` — общий поток ТС/униформы: решение `PENDING/APPROVED/REJECTED`, `decided_at`, `expires_at`, расположение review-сообщения (`review_guild_id/channel_id/message_id`) и id кнопок; одна `ACTIVE` регистрация типа на персонажа, отказ закрывает запись (`CLOSED`);
- `transfers` — решения обеих сторон и кто их принял, расположение review-сообщения, одна `PENDING` заявка на персонажа;
- `media_files`, `webhook_requests`, `ic_blacklist`, `role_panels`, `feedback_tickets/messages`, `forms/form_fields/form_submissions`.

Дополнительно: `forms.delivery_channel_id` (`20261003090000_form_delivery_channel`) — доставка ответа формы в канал ботом.

Частичные индексы Prisma-схемой не выражаются и заданы в SQL миграции. При генерации следующих миграций `prisma migrate dev` может предложить их удалить — такие строки из сгенерированного SQL нужно убирать.

## Исправлено после обзора

- повторная выдача нашивки после `/token remove` (раньше — unique violation на `tokens.character_id`);
- решения по регистрации атомарны (`updateMany` с условием `PENDING`), по переводу — под `SELECT … FOR UPDATE`: параллельные одобрения обеих сторон не теряются, перевод не зависает в `PENDING`;
- кнопки ревью учитывают `SUPER_ADMIN_USER_IDS` из env;
- review-сообщения рендерятся из БД: исходный текст заявки сохраняется, решение и автор дописываются, кнопки убираются (перевод — блокируется сторона, принявшая решение);
- кнопки ревью и job доставки создаются в той же транзакции, что и заявка; job идемпотентен (пропускает, если id сообщения уже сохранён);
- ошибки кнопок и модалок отвечают пользователю эфемерным сообщением на русском вместо «Interaction failed»;
- лимит ответов формы проверяется под блокировкой строки формы;
- `/создать-webhook` вне сервера отклоняется; лог регистрации команд пишет реальное число команд; lint для `scripts/` разрешает `console`.

## Сделано по плану

- `/персонаж создать|список|статик` (статик — админ), `/token receive|get|find|remove`;
  - формат нашивки `[Фракция | Отдел | номер]`; длина 4 → 5 → 6 при пороге `tokens.expandThresholdPercent`;
  - `token find` для админов и ролей `tokens.finderRoleIds`; кнопка `token.receive` (модалка со статиком) для закреплённого сообщения;
- `/регистрация-тс`, `/регистрация-формы` (§4.5–4.6):
  - фото как Discord-вложение → `media_files` (только CDN Discord, лимит 10 МБ, изображения);
  - госномер нормализуется и уникален среди ACTIVE ТС; модель — автодополнение из `vehicle_models` (пустой каталог = свободный текст);
  - review в канале ЧП с пингом `registrations.coordinatorRoleIds`, публичная ветка, кнопки approve/reject;
  - одобрение → краткая карточка и TTL `registrations.ttlDays` (31); отказ → причина в ветке и ЛС;
  - истечение по таймеру обслуживания бота: статус EXPIRED, правка карточки, ЛС игроку;
- `/перевод-фракции` (§4.8):
  - таблица `transfer_rank_rules` (пустая пара фракций = свободные ранги);
  - проверка членства заявителя во фракции «из» (админы обходят);
  - фото документов через `media_files`; автодополнение фракций;
  - review с пингом ролей лидеров обеих фракций, двойное одобрение;
  - ЛС после закрытия заявки (`transfers.approvalDmText` при одобрении; причина при отказе);
- `/создать-webhook` (§4.7): бот создаёт Discord webhook в канале, сохраняет URL в `webhook_requests`, уведомляет админов в `webhooks.notifyChannelId`;
- IC чёрный список (§4.13): `/чс-добавить|снять|найти`, роли `icBlacklist.managerRoleIds` / `searchRoleIds`, доказательства-фото, пометка в `/персонаж список`, истечение по TTL;
- `/проверить-фракции`, `/инвайт-админ` (§4.11): пересечения состава по role_mappings; временные инвайты на серверы из `invites.guildIds`;
- §4.14 панели ролей:
  - публикация/архив через `ROLE_PANEL_PUBLISH` / `ROLE_PANEL_ARCHIVE`;
  - `role.toggle` с `allowedRoleIds` (кто может нажимать) и `exclusiveRoleIds` (взаимоисключающие);
  - создание/архив из `/settings/stage4` и ограничения в embed button-manager;
- §4.14 формы в Discord (до 5 полей — лимит одной модалки):
  - `form.open` / `form.submit`, сохранение в БД с аудитом;
  - доставка ответа в канал и/или webhook через `FORM_SUBMISSION_DELIVER`;
- §4.14 обратная связь:
  - `feedback.open` → тикет; `FEEDBACK_TICKET_NOTIFY` в `feedback.notifyChannelId`;
  - ответ админа → `FEEDBACK_REPLY_SEND` в ЛС; закрытие → `FEEDBACK_CLOSED_SEND` в ЛС;
  - UI тикетов в `/settings/stage4`;
- `/settings/stage4`, `/settings/tokens`, `/settings/registrations` — рабочие настройки Stage 4
  (`registrations.*`, `transfers.*`, `feedback.notifyChannelId`, IC blacklist roles, invites, tokens).
