# Mirror: перенос на сервер, домен, обновление

Документ для того, кто разворачивает проект: что купить, какие команды выполнить, как привязать домен и как потом обновлять и чинить. Устройство системы изнутри описано в [TECHNICAL.md](TECHNICAL.md).

> **Статус проверки (без изменений с 3 октября 2026).** Скрипты из папки `deploy/` проверены на синтаксис, конфигурация Caddy — валидатором Caddy, сервис резервных копий и восстановление — на локальном Docker, production-сборка — локально. **На настоящем сервере Ubuntu скрипты `setup.sh`, `update.sh` и `set-domain.sh` целиком ещё не запускались** — первый запуск делайте внимательно и читайте вывод.

## 1. Что получится

```text
Интернет ──443──▶ Caddy (HTTPS, сертификат сам) ──▶ дашборд Next.js  127.0.0.1:3000  (systemd: mirror-dashboard)
                                                    бот Discord                      (systemd: mirror-bot)
                                                    PostgreSQL       127.0.0.1:5432  (Docker)
                                                    хранилище S3     127.0.0.1:9000  (Docker, SeaweedFS)
                                                    резервные копии                  (Docker, раз в сутки)
```

Наружу открыты только порты 22 (SSH), 80 и 443. База и хранилище слушают только локальный адрес.

| Что | Где на сервере |
|---|---|
| Код проекта | `/opt/mirror` |
| Настройки и секреты | `/opt/mirror/.env` (права 600, владелец `mirror`) |
| Службы | `mirror-bot`, `mirror-dashboard`, `caddy`, `docker` |
| Данные базы, файлы, копии | тома Docker `mirror_mirror-postgres`, `mirror_mirror-storage`, `mirror_mirror-backups` |
| Конфигурация прокси | `/etc/caddy/Caddyfile` |
| Журналы | `journalctl -u mirror-bot`, `journalctl -u mirror-dashboard`, `/var/log/caddy/` |

## 2. Что нужно заранее

1. **Сервер (VPS)** с Ubuntu 22.04 или 24.04, от 2 ГБ памяти (сборка дашборда требует около 1,5 ГБ), 20 ГБ диска, публичный IPv4, доступ по SSH с правами `sudo`.
2. **Приложение Discord** — https://discord.com/developers/applications:
   - раздел **Bot**: скопировать **Token**; включить **Server Members Intent**;
   - раздел **OAuth2**: скопировать **Client ID** и **Client Secret**;
   - бот должен быть добавлен на все серверы проекта с правами: управление ролями, исключение участников, управление вебхуками, отправка сообщений, встраивание ссылок, создание приглашений, создание веток. Роль бота на каждом сервере должна стоять **выше** ролей, которыми он управляет.
3. **Discord ID главных администраторов** (правый клик по пользователю → «Копировать ID» при включённом режиме разработчика).
4. **Домен** — необязателен в первый день. Без него сайт заработает на временном адресе вида `203-0-113-10.sslip.io` с настоящим HTTPS.

> ⚠️ Токен старого Python-бота лежал в файле `.env.legacy` открытым текстом. Перед запуском **перевыпустите токен** в Developer Portal (Bot → Reset Token) и используйте только новый. Файл `.env.legacy` на рабочем компьютере после этого удалите.

## 3. Первая установка — одна команда

### 3.1 Загрузить код на сервер

Вариант А — из Git (предпочтительно: потом обновление будет одной командой):

```bash
sudo REPO_URL=https://github.com/<владелец>/<репозиторий>.git bash -c 'apt-get update -y && apt-get install -y git && git clone "$REPO_URL" /opt/mirror'
```

Вариант Б — репозитория в сети нет. С рабочего компьютера (из папки проекта):

```bash
scp -r . user@SERVER_IP:/tmp/mirror-src
```

Каталоги `node_modules`, `.next`, `dist` и файл `.env` копировать не нужно — скрипт их пропустит. Без Git на сервере обновление командой `update.sh` работать не будет: для обновлений нужен вариант А.

### 3.2 Запустить установку

```bash
# вариант А
sudo bash /opt/mirror/deploy/setup.sh

# вариант Б
sudo bash /tmp/mirror-src/deploy/setup.sh
```

Сразу с доменом (A-запись уже должна указывать на сервер, см. раздел 4):

```bash
sudo DOMAIN=mirror.example.com bash /opt/mirror/deploy/setup.sh
```

Скрипт можно запускать повторно — он ничего не ломает и не перезаписывает `.env`. Что он делает по шагам:

1. ставит системные пакеты, Node.js 22, pnpm (версия из `package.json`), Docker, Caddy;
2. создаёт пользователя `mirror` и кладёт код в `/opt/mirror`;
3. определяет адрес сайта: `DOMAIN`, либо временный `<ip>.sslip.io`;
4. создаёт `/opt/mirror/.env` из `deploy/env.production.example` и **генерирует** пароли базы, хранилища и секрет сессий;
5. поднимает в Docker базу, хранилище и сервис резервных копий;
6. ставит зависимости, применяет миграции базы, собирает проект;
7. ставит службы systemd `mirror-bot` и `mirror-dashboard` (перезапуск при сбое, запуск при загрузке сервера);
8. настраивает Caddy (HTTPS) и файрвол `ufw` (SSH, 80, 443).

### 3.3 Вписать секреты Discord

```bash
sudo nano /opt/mirror/.env
```

Заполнить четыре строки:

```ini
DISCORD_BOT_TOKEN=...            # Bot → Token
DISCORD_CLIENT_ID=...            # OAuth2 → Client ID
DISCORD_CLIENT_SECRET=...        # OAuth2 → Client Secret
SUPER_ADMIN_USER_IDS=111111111111111111,222222222222222222
```

Необязательно, но нужно для юридических страниц (`/terms`, `/privacy`):

```ini
LEGAL_OPERATOR_NAME=...          # кто управляет сервисом
LEGAL_CONTACT_EMAIL=...          # адрес для обращений
LEGAL_GOVERNING_LAW=...          # фраза, например: законодательство Российской Федерации
```

### 3.4 Разрешить адрес в Discord

Developer Portal → приложение → **OAuth2 → Redirects → Add Redirect**:

```text
https://<адрес-сайта>/api/auth/callback/discord
```

Адрес должен совпадать со значением `OAUTH_REDIRECT_URL` в `.env` символ в символ.

### 3.5 Запустить

```bash
sudo bash /opt/mirror/deploy/update.sh start
```

Команда создаёт начальные данные (фракции, настройки по умолчанию, главные администраторы), запускает бота и дашборд и ждёт, пока оба ответят.

### 3.6 Первичная настройка в дашборде

Откройте сайт, войдите через Discord аккаунтом из `SUPER_ADMIN_USER_IDS` и пройдите по разделам:

1. **Настройки** — вкладка «Серверы и синхронизация»: главный сервер и сервер ЧП; вкладка «Защита и мониторинг»: канал ошибок бота и вебхук оповещения «бот не отвечает».
2. **Фракции** — вкладки «Роли» (привязка ролей Discord к уровням доступа и фракциям), «Каналы фракций» (документы и кадровый аудит), «Права команд».
3. **Модули** — каналы и роли каждого модуля: документы, розыск, регистрации, переводы, IC ЧС, нашивки, обратная связь.
4. **Настройки → Тексты и данные** — юридические тексты, если нужны свои.
5. Раздел **FAQ** уже заполнен справкой для игроков, сотрудников и администраторов — проверьте её и поправьте под свои правила.
6. На сервере выполните `sudo bash /opt/mirror/deploy/update.sh status` — все строки должны быть `ok`; «Резервные копии» появятся после первой копии (сразу после запуска).

Пока главный сервер не выбран, войти может только главный администратор — это нормально.

## 4. Привязка домена

### 4.1 DNS

У регистратора домена создайте запись:

| Тип | Имя | Значение | TTL |
|---|---|---|---|
| A | `mirror` (для `mirror.example.com`) или `@` (для самого домена) | IP сервера | 300 |

Проверка (должен вернуться IP сервера):

```bash
dig +short mirror.example.com
```

Если домен обслуживает Cloudflare: на время получения сертификата поставьте запись в режим **DNS only** (серое облако). После того как сайт открылся по HTTPS, можно включить проксирование, выбрав в Cloudflare режим SSL **Full (strict)**.

### 4.2 Переключить сайт на домен

```bash
sudo bash /opt/mirror/deploy/set-domain.sh mirror.example.com
```

Скрипт проверяет DNS, записывает новый адрес в `.env` (`PUBLIC_BASE_URL`, `OAUTH_REDIRECT_URL`) и в конфигурацию Caddy, перезапускает дашборд и бота и ждёт ответа по HTTPS. Сертификат Let's Encrypt Caddy получает и продлевает сам. Прежний `.env` сохраняется рядом как `.env.before-domain`.

### 4.3 Обновить Discord

Developer Portal → **OAuth2 → Redirects** → добавить:

```text
https://mirror.example.com/api/auth/callback/discord
```

Старый адрес удалите после того, как убедитесь, что вход работает.

### 4.4 Что ещё меняется при смене адреса

- Все пользователи входят заново: сессии привязаны к адресу сайта.
- Ссылки на веб-формы в **новых** сообщениях бота ведут на новый адрес. Сообщения, опубликованные раньше со старым адресом, нужно опубликовать заново из дашборда (раздел «Формы»).
- Публичные ссылки «поделиться» (`/s/…`) продолжают работать на новом адресе: меняется только доменная часть.

### 4.5 Вернуть прежний адрес

```bash
sudo bash /opt/mirror/deploy/set-domain.sh 203-0-113-10.sslip.io
```

## 5. Обновление — одна команда

```bash
sudo bash /opt/mirror/deploy/update.sh
```

Что происходит:

1. включаются технические работы — сайт и команды бота закрыты для всех, кроме главных администраторов; посетители видят страницу «Технические работы»;
2. делается резервная копия базы и файлов;
3. `git pull` — получение новой версии;
4. установка зависимостей, пересборка служебных контейнеров;
5. миграции базы данных;
6. сборка бота и дашборда;
7. перезапуск служб;
8. проверка: сайт отвечает на `/api/health`, бот прислал сигнал «жив»;
9. технические работы выключаются.

**Если шаг не удался**, скрипт останавливается, пишет, на каком шаге, и **оставляет технические работы включёнными** — пользователи не увидят наполовину обновлённую систему. Дальше одно из трёх:

```bash
sudo bash /opt/mirror/deploy/update.sh            # исправили причину — повторить
sudo bash /opt/mirror/deploy/update.sh rollback   # вернуть код к версии до обновления
sudo bash /opt/mirror/deploy/update.sh disable    # открыть сайт как есть
```

Все команды скрипта:

| Команда | Что делает |
|---|---|
| `update.sh` | полное обновление |
| `update.sh status` | версия, адрес, состояние служб, бот, очередь, хранилище, резервные копии |
| `update.sh enable "причина"` | включить технические работы вручную |
| `update.sh disable` | выключить технические работы |
| `update.sh start` / `stop` / `restart` | бот и дашборд |
| `update.sh logs` / `logs bot` / `logs dashboard` | журналы в реальном времени |
| `update.sh backup` | резервная копия сейчас |
| `update.sh rollback` | вернуть код к версии до последнего обновления |

Пока дашборд перезапускается (несколько секунд), Caddy показывает страницу «Идёт обновление» вместо ошибки 502.

### Откат

`rollback` возвращает **код** к версии, записанной перед последним обновлением, пересобирает и перезапускает. Миграции базы назад не откатываются: они только добавляют таблицы и столбцы, и прежний код продолжает с ними работать. Если обновление изменило данные несовместимо, восстановите копию, сделанную перед обновлением (раздел 6.3).

## 6. Резервные копии

Сервис `backup` в Docker Compose работает сам:

- каждый день в **04:00 по Москве** — дамп базы (`pg_dump`, свой формат) и копия файлов хранилища;
- дампы хранятся **14 дней**; копия файлов — зеркало: проект не удаляет файлы, поэтому зеркало содержит состояние на любой день;
- копия также делается при первом запуске и перед каждым обновлением;
- результат каждой копии виден в `update.sh status`; если копий не было больше суток — строка помечена «СБОЙ».

Время и срок меняются в `.env`: `BACKUP_AT=04:00`, `BACKUP_KEEP_DAYS=14`, затем `cd /opt/mirror && sudo docker compose up -d backup`.

### 6.1 Посмотреть копии

```bash
cd /opt/mirror
sudo docker compose exec backup sh -c 'ls -lh /backups/db; du -sh /backups/storage'
```

### 6.2 Проверить, что копия восстанавливается

```bash
sudo docker compose exec backup verify.sh
```

База данных в `docker-compose.yml` запущена с защитными настройками: запись на диск подтверждается всегда (данные не теряются при сбое питания), транзакция, оставленная открытой без дела дольше минуты, завершается сама, а запросы дольше секунды, ожидания блокировок и контрольные точки пишутся в журнал — `sudo docker compose logs postgres`. Если сайт «задумался», смотреть нужно туда.

Скрипт разворачивает последний дамп во временную базу, сравнивает число строк в каждой таблице с рабочей базой и удаляет временную базу. Рабочая база не затрагивается. Делайте это после установки и раз в месяц.

### 6.3 Восстановить

```bash
sudo bash /opt/mirror/deploy/update.sh enable "Восстановление из резервной копии"
sudo bash /opt/mirror/deploy/update.sh stop

cd /opt/mirror
sudo docker compose exec backup restore.sh --yes                               # последняя копия: база + файлы
sudo docker compose exec backup restore.sh --yes mirror-20261003-040000.dump   # конкретный дамп
sudo docker compose exec backup restore.sh --yes --db-only                     # только база
sudo docker compose exec backup restore.sh --yes --storage-only                # только файлы

sudo bash /opt/mirror/deploy/update.sh start
sudo bash /opt/mirror/deploy/update.sh disable
```

Перед заменой базы скрипт сохраняет её текущее состояние в `/backups/db/before-restore-….dump` — если восстановили не то, можно вернуться.

### 6.4 Хранить копии вне сервера

Копии лежат на том же сервере: если сервер потерян, потеряны и они. Раз в сутки забирайте их на другую машину — например, с домашнего компьютера или второго сервера по расписанию:

```bash
ssh user@SERVER_IP 'sudo docker run --rm -v mirror_mirror-backups:/b alpine tar -C /b -czf - .' > mirror-backups-$(date +%F).tar.gz
```

## 7. Перенос на другой сервер

1. На новом сервере выполните установку (раздел 3) до шага 3.5 включительно **не запуская** `update.sh start`.
2. На старом сервере включите техработы, остановите службы и сделайте копию:

   ```bash
   sudo bash /opt/mirror/deploy/update.sh enable "Переезд на новый сервер"
   sudo bash /opt/mirror/deploy/update.sh stop
   sudo bash /opt/mirror/deploy/update.sh backup
   sudo docker run --rm -v mirror_mirror-backups:/b alpine tar -C /b -czf - . > /tmp/mirror-backups.tar.gz
   ```

3. Перенесите архив и распакуйте его в том резервных копий нового сервера:

   ```bash
   scp /tmp/mirror-backups.tar.gz user@NEW_IP:/tmp/
   # на новом сервере:
   sudo docker run --rm -v mirror_mirror-backups:/b -v /tmp:/in alpine tar -C /b -xzf /in/mirror-backups.tar.gz
   ```

4. Скопируйте со старого сервера в новый `.env` значение `SESSION_SECRET` (иначе все сессии станут недействительными — это не страшно, пользователи просто войдут заново) и четыре значения Discord. Пароли базы и хранилища **не переносите**: на новом сервере они свои.
5. Восстановите данные и запустите:

   ```bash
   cd /opt/mirror
   sudo docker compose exec backup restore.sh --yes
   sudo bash /opt/mirror/deploy/update.sh start
   sudo bash /opt/mirror/deploy/update.sh disable
   ```

6. Переключите A-запись домена на новый IP и выполните `set-domain.sh` на новом сервере.
7. Старый сервер держите выключенным (службы `mirror-bot` остановлена!) — два бота с одним токеном одновременно работать не должны.

## 8. Повседневное обслуживание

| Задача | Команда |
|---|---|
| Всё ли работает | `sudo bash /opt/mirror/deploy/update.sh status`; в дашборде о сбоях сообщает колокольчик уведомлений |
| Журнал бота | `sudo bash /opt/mirror/deploy/update.sh logs bot` |
| Журнал сайта | `sudo bash /opt/mirror/deploy/update.sh logs dashboard` |
| Журнал прокси и сертификатов | `sudo journalctl -u caddy -n 100` |
| Перезапустить | `sudo bash /opt/mirror/deploy/update.sh restart` |
| Закрыть сайт и бота на время работ | `update.sh enable "причина"` или переключатель в **Настройки → Защита и мониторинг** |
| Сменить секрет Discord | поправить `/opt/mirror/.env`, затем `update.sh restart` |
| Место на диске | `df -h`, `sudo docker system df` |
| Обновления системы | `sudo apt update && sudo apt upgrade` |

Оповещения, которые приходят сами (настраиваются в **Настройки → Защита и мониторинг**):

- ошибки бота и задачи, не выполненные после всех попыток, — в выбранный канал Discord;
- «бот не отвечает» — на вебхук Discord, одно сообщение на каждое отключение; отправляет сайт, поэтому оно придёт, даже если бот упал.

## 9. Если что-то не работает

| Симптом | Что проверить |
|---|---|
| Сайт не открывается вообще | `systemctl status caddy`; открыты ли 80 и 443 у провайдера (группа безопасности / файрвол в панели VPS); `dig +short домен` |
| «Идёт обновление» дольше минуты | дашборд не запущен: `update.sh logs dashboard` |
| Ошибка сертификата | DNS ещё не указывает на сервер или закрыт порт 80: `journalctl -u caddy -n 50` |
| После входа через Discord — ошибка `redirect_uri` | адрес в OAuth2 → Redirects не совпадает с `OAUTH_REDIRECT_URL` в `.env` |
| Вход возвращает на страницу «Нет доступа» | главный сервер не выбран (войти может только главный администратор) или у аккаунта нет ролей; технический бан |
| Все видят «Технические работы» | остались включены после неудачного обновления: `update.sh status`, затем `update.sh disable` |
| Бот в сети, но команды молчат | включены техработы; у аккаунта технический бан; бот не добавлен на сервер; `update.sh logs bot` |
| Бот не выдаёт роли / не исключает | роль бота ниже управляемых ролей или нет прав; сообщение об этом — в канале ошибок |
| Сообщения в Discord не появляются | дашборд → **Очередь задач**: «Отложено» — не настроен канал; «Упала» — причина в столбце «Сообщение», после исправления «Повторить» |
| `update.sh` остановился на «Миграции базы данных» | `update.sh logs`; база не изменена частично — миграция идёт в транзакции; исправить и повторить либо `rollback` |
| Служба постоянно перезапускается | `journalctl -u mirror-bot -n 80`; чаще всего — не заполнен или неверен `.env` |
| Закончилось место | `sudo docker system prune`; уменьшить `BACKUP_KEEP_DAYS`; увеличить диск |

## 10. Справочник переменных `.env`

| Переменная | Обязательна | Назначение |
|---|---|---|
| `APP_ENV` | да | `production` |
| `LOG_LEVEL` | нет | `info` по умолчанию |
| `DISCORD_BOT_TOKEN` | да | токен бота |
| `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` | да | вход через Discord |
| `SUPER_ADMIN_USER_IDS` | да | Discord ID главных администраторов через запятую |
| `PUBLIC_BASE_URL` | да | адрес сайта, как его открывают посетители; из него бот строит ссылки на веб-формы |
| `OAUTH_REDIRECT_URL` | да | `<адрес>/api/auth/callback/discord` |
| `SESSION_SECRET` | да | подпись сессий; создаётся установкой |
| `POSTGRES_PASSWORD`, `DATABASE_URL` | да | база; создаются установкой, пароль в обеих строках один |
| `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` | да | хранилище файлов; создаются установкой |
| `BACKUP_AT`, `BACKUP_KEEP_DAYS` | нет | время ежедневной копии и срок хранения дампов |
| `LEGAL_OPERATOR_NAME`, `LEGAL_CONTACT_EMAIL`, `LEGAL_GOVERNING_LAW` | нет | данные оператора для юридических страниц |

`POSTGRES_PASSWORD` и ключи S3 **нельзя менять после первого запуска** простой правкой `.env`: база и хранилище запомнили прежние значения. Всё остальное (серверы, роли, каналы, сроки) настраивается в дашборде и в `.env` не хранится.
